## 2. Architecture as actually built

**Stack:** Expo **SDK 54** (pinned — see §4, this matters), TypeScript, Expo Router, expo-sqlite + Drizzle ORM, NativeWind, Zustand, Moti/Reanimated, react-native-svg + expo-linear-gradient (progress indicators), Jest for pure-logic unit tests. Full rationale in [`TECH-STACK.md`](./TECH-STACK.md).

**Data layer** (`lib/goals.ts` is the center of gravity):
- `db/schema.ts` — full brief §5 schema (goals, completion_log) plus a `settings` single-row table (not in brief §5 — device-local prefs kept in the same SQLite DB rather than a second storage engine, per the "SQLite is the only storage layer" constraint). Five migrations applied (`db/migrations/000{0,1,2,3,4}_*.sql`).
- `getTree(parentId, { includeArchived })` — the one function nearly every screen calls. Returns `GoalTreeNode[]`: each node's full subtree, progress, `lastActivityAt` (staleness signal), and `recurringCompletedToday`, all computed in one recursive DB pass via the internal `computeSubtreeStats`.
- **Progress and staleness are always computed archived-excluded**, independent of whatever the "show archived" *display* toggle is set to. This was a real bug (found and fixed): a display preference was silently changing percentages. If you touch `computeSubtreeStats` or `listChildren` calls, preserve this separation.
- Recurring nodes report a trailing-window completion rate (`lib/completionLog.ts:getTrailingCompletionRate`) as their progress instead of averaging children — their own children (rotation-cycle members) are never separately rolled up into a parent average.
- Pure logic lives in dedicated files with **no DB import**, each with its own Jest suite: `lib/rollup.ts`, `lib/cycles.ts`, `lib/staleness.ts`, `lib/surfacing.ts`, `lib/streakIntensity.ts`, `lib/colorPalette.ts` (`withAlpha`), `components/indicators/geometry.ts`. This split is deliberate (see [`TESTING.md`](./TESTING.md)) — `lib/goals.ts`/`completionLog.ts`/`settings.ts` touch `expo-sqlite` directly and are **not** unit-tested; their correctness has been verified via typecheck + bundle + repeated independent code review instead. (`lib/accentColor.ts` — formerly in this list — was deleted; see the accent-color entry in §3.)

**Screens** (`app/` routes, `components/*Screen.tsx` implementations):
- `/` (Home) — greeting + brief §6's daily-surfacing list (`lib/home.ts` bridges the flat DB into `lib/surfacing.ts`'s pure algorithm) + CTA.
- `/explorer` and `/explorer/[id]` — Drill-down. For a non-root node this screen *is* Node Detail too: editable title/description, `ScheduleEditor` (schedule type + type-specific fields), lifecycle actions, Move, Delete, children list with add-bar.
- `/outline` — whole-tree indented view, same underlying data, its own `TreeRow` recursion (not `GoalRow` — duplicated glyph logic, see §3).
- `/settings`, `/search`, `/move/[id]`, `/streaks/[id]` — self-explanatory from the file name.
- `components/GoalRow.tsx` — the shared row component used by the Explorer's list (not by Outline).

**State:** `store/settings.ts` is currently the only Zustand store — loaded once at app startup in `app/_layout.tsx`, gates rendering until loaded (`settings === null` never reaches a screen). Theme syncs to NativeWind's `colorScheme` there too.

## 3. Judgment calls made where the brief was silent or ambiguous

Each of these is also commented in the code at its point of decision — this is a summary, not the only record.

- **Cascade delete.** Deleting a node deletes its whole subtree (DB `onDelete: 'cascade'`), with a UI confirmation warning when the node has children. Brief didn't specify; this was the direct reading of "deletion can be a real local delete."
- **One-shot leaf completion drives `lifecycle_state`.** Toggling a leaf's `is_complete` also flips `lifecycle_state` between `active`/`complete`. Recurring leaves use a *different* path entirely (`markRecurringCompleteToday`, logs to `completion_log`, never touches `is_complete`/`lifecycle_state` — brief §3: recurring nodes have no natural Complete state). This was itself the subject of a real bug: earlier code routed recurring-leaf row taps through the one-shot toggle, which could permanently strand a habit in `'complete'`. Fixed.
- **No cached progress column.** Computed on demand (`computeSubtreeStats`), matching brief §5's literal schema (which has no such column) over §2's prose mention of caching as a future optimization.
- **Accent color is hashed from the root goal's id, not creation-order-indexed.** Brief §11 floats creation-order as a *proposed* (not mandated) default; hashing avoids every other root's color reshuffling when one root is deleted. **Superseded** (post-MVP follow-up, user-directed): replaced with three independently user-selectable *global* colors (progress bar/ring, streak calendar, checkbox) stored on the `settings` row (`progressColor`/`calendarColor`/`checkboxColor`, migration `0003`), not per-root-goal at all. This is a deliberate departure from brief §8.4's "one color family per branch" framing — the user was shown that conflict explicitly and chose the global-three-color model anyway. `lib/accentColor.ts` (the hash function) was deleted; swatches now live in `lib/colorPalette.ts`.
- **Reorder is swap-with-neighbor (▲/▼ buttons), not drag-and-drop.** No gesture library is in the dependency set; a swap reaches the same end state via repeated taps. Scoped to the Drill-down list only — Outline's rows are already dense.
- **No native date picker.** Date-range/recurring "started on" fields are validated `YYYY-MM-DD` text inputs (validation tightened once to reject calendar overflow like Feb 30). A real date-picker component would be a nicer follow-up.
- **Parent nodes of any schedule type never manually reach `'complete'`.** Only leaves get the manual complete action. This is symmetric across one-shot and date-range (an earlier review flagged date-range parents specifically; the correct read was that this is consistent existing behavior, not a new gap — fixing it just for date-range would have *introduced* an inconsistency).
- **Settings screen exposes `staleDays`/`dueSoonHours`/`recurringWindowDays` thresholds** per brief's own Settings screen spec, even before Phase 1.5 consumed them (they were added in the MVP-completion pass, wired up properly once Phase 1.5 landed).
- **Recurring nodes now have two modes: `rotation` (original, brief §4's one-due-child-per-day cycle) and `checklist` (new, user-directed).** In checklist mode every `cyclePattern` member is due every day, tracked independently via a new `logChecklistCompletion`/`getChecklistDayFractions` upsert-by-`(goalId, date, childId)` path in `lib/completionLog.ts` (rotation's `logCompletion` still upserts by `(goalId, date)` only — untouched). Schema: `goals.recurring_mode` (migration `0004`, default `'rotation'`, so every existing recurring node's behavior is unchanged). A checklist node's own rollup contribution is `getChecklistTrailingRate` — the trailing-window *average daily checked-fraction* — deliberately parallel to rotation's `getTrailingCompletionRate` (both divide by the full window, not just logged days, so unlogged days count as 0). `ScheduleEditor` gained a Rotation/Checklist mode toggle and a per-member daily checkbox list (checklist) alongside the existing rotation UI. This is a genuine new product surface, not calendar styling — flagged as such mid-implementation (crosses into Phase-1.5-groundwork territory per brief §4's rotation-only recurring definition) and built anyway on explicit user direction after the tradeoff was shown.
- **Streak calendar intensity is derived from the user's own `calendarColor` setting, not a hardcoded green**, even though the original ask described "light green / pale green / bright green." Since `calendarColor` is now user-selectable (see accent-color entry above), three fixed green shades would visually clash with a user-chosen non-green calendar color — `lib/colorPalette.ts:withAlpha` derives low/medium/high as 30%/65%/100% opacity of whatever `calendarColor` is set to (bucketed by `lib/streakIntensity.ts:bucketIntensity`, thresholds <25%/<75%/≥75%). Rotation-mode's existing binary completed/missed/no-data coloring is unchanged. All calendar cells (including missed/no-data) now get a thin light border regardless of mode.
- **Bug found by independent review, fixed same round:** Home's tap-to-complete (`app/index.tsx:handleToggle`) called the rotation-only `markRecurringCompleteToday` for *every* surfaced recurring goal, including checklist-mode ones. Since `logCompletion` upserts by `(goalId, date)` with no `childId` filter, this could silently no-op (write an orphaned `childId: null` row the checklist readers filter out) or — worse — overwrite an existing per-member row's `childId` to `null`, un-marking a check the user had already made via Node Detail. Fixed by routing checklist-mode taps from Home to Node Detail instead of toggling blindly, since one checkbox can't represent "which member(s)" for a multi-member checklist day. Also hardened `getTrailingCompletionRate` to count distinct completed *dates* rather than raw rows, so a node's history staying correct even if it's ever switched from checklist back to rotation (checklist can log several rows per date; rotation's model assumes at most one).
- **App-wide font/UI scale setting, via NativeWind's `rem` observable rather than per-component edits.** `settings.fontScale` (migration `0005`, one of `FONT_SCALE_STEPS = [0.85, 1, 1.15, 1.3]`, default `1`) drives a single `rem.set(BASE_REM * settings.fontScale)` effect in `app/_layout.tsx` — NativeWind v4 resolves every rem-based Tailwind utility (`text-*`, `p-*`/`px-*`/`py-*`, `gap-*`, `rounded-*`, numeric `w-*`/`h-*`) against this one reactive value at render time, so the whole app rescales without touching any of the ~15 components that use those classes. `BASE_REM` is captured once via `rem.get()` at module load (NativeWind's own default, 14) rather than hardcoded, so this stays correct if that default ever changes upstream. Exposed in Settings via a new "Text size" segmented control, reusing the existing `SegmentedOption` pattern (its generic was loosened from `T extends string` to `T` to accept the numeric scale values) rather than introducing a new slider primitive Klados doesn't otherwise have.
  - **Operational gotcha, cost a full user-facing round-trip to find (worth its own callout like §4's SDK-pinning one):** the first pass of this feature shipped with no visible effect — the setting UI worked, `rem.set()` ran without error, nothing on screen changed. Root cause: `metro.config.js`'s `withNativeWind(config, { input: './global.css' })` call didn't pass `inlineRem`, so it silently defaulted to `inlineRem: 14` (see `node_modules/nativewind/dist/metro/index.js`). With that default, NativeWind's build-time compiler (`css-to-rn/parseDeclaration.js`'s `case "rem"`) bakes every rem-based utility value into a **static pixel number at build time** rather than emitting the runtime-resolvable `[{}, "rem", [value]]` tuple `resolve-value.js` reads via `rem.get()`. So the whole `rem` observable mechanism is real and works exactly as documented — it just had nothing left to affect, since all the styles were already frozen into plain numbers before the app ever ran. Fixed with one line: `withNativeWind(config, { input: './global.css', inlineRem: false })`. **If a future dynamic-styling feature via NativeWind's runtime primitives (`rem`, `vars()`, etc.) seems to have no effect, check `metro.config.js`'s `withNativeWind` options for `inlineRem` before assuming the mechanism itself is broken.**
- **Tap-target sizing pass**, addressing brief §8's own "comfortable thumb-sized tap targets" line (a real gap against spec, not just a preference): `GoalRow`'s stacked ▲/▼ reorder buttons had zero gap between them and `hitSlop={4}` each — the most likely single cause of mis-taps — now have a real gap plus `hitSlop={10}`/padding. Every icon-only `Pressable` across the header rows (search/settings in `ExplorerScreen`/`OutlineScreen`, `ModeToggle`'s Tree/Outline segments, every screen's `‹ Back`) got consistent padding + `hitSlop={10}`. This is independent of and complementary to the font-scale setting above — padding/gap classes benefit from `rem` scaling too, but the baseline sizing needed fixing regardless of what scale a user picks.
- **Parent-node folder glyph and recurring 🔁 emoji replaced with minimal outline icons** (`@expo/vector-icons`'s Feather set — folder/repeat, imported from its per-family subpath `@expo/vector-icons/Feather` rather than the package's barrel export, which would otherwise bundle every icon family's font file into the app for ~400KB of dead weight), moved from *before* the title to a small caption row *below* it in `GoalRow` (Drill-down's rows). `OutlineScreen`'s `TreeRow` gets the repeat-icon caption too, but deliberately *not* a folder caption — Outline already relies on its own leading `▸` chevron to signal "parent," and PROGRESS.md's own reorder-scoping note above already established Outline's rows as "already dense" (brief §8.2); adding a second parent-indicator glyph there would be piling onto that density rather than fixing it. This is a conscious asymmetry between the two view modes, not an oversight.
- **Add-goal bar moved from the bottom of Explorer/Node-Detail to a fixed row directly under the breadcrumb header**, always visible without scrolling, per explicit user request for easier access. **Bug found by independent review, fixed same round:** the first pass added the new top bar but left the old bottom one in place, producing two identical "Add a goal…" inputs on screen — both wired to the same `newTitle` state/`handleAdd` handler, so no functional corruption, just a visible duplicate. Removed the bottom copy. `KeyboardAvoidingView` still wraps the `FlatList` below (kept for the title/description fields' own keyboard behavior via RN's built-in scroll-focused-input-into-view), it just no longer has anything of its own to protect from the keyboard since the add bar moved out from under that concern entirely.
- **Home's "Get me there" CTA moved off the bottom edge to vertically centered**, per user request. Restructured `app/index.tsx` around a single outer `ScrollView` (`contentContainerStyle={{flexGrow:1}}`, carrying the pull-to-refresh `RefreshControl` that used to live on the inner `FlatList`) so the CTA's wrapping `View` (`flex-1 items-center justify-center`) can claim and center within whatever vertical space the (now natural-height, capped-~5-item) Today list didn't use. The Today list itself switched from `FlatList` to a plain `.map()` — nesting a virtualized list inside a `ScrollView` is an anti-pattern RN warns about, and at a ~5-item cap there's no virtualization benefit to lose. **Gap found by independent review, fixed same round:** the restructure silently dropped the "Nothing due today." empty-state message (the whole Today section was gated on `tasks.length > 0`, so an empty day showed nothing at all where explanatory text used to be). Restored — the Today section always renders now, showing either the list or that message.
- **Edge-swipe-right-to-go-back added to the Explorer/Node-Detail screen**, via React Native's built-in `PanResponder` (no new native dependency — `react-native-gesture-handler` isn't in this project and would need a native rebuild; native-stack's own Android gesture support was also uncertain enough not to lean on, especially with `app.json`'s `predictiveBackGestureEnabled: false` already opting out of Android's system-level equivalent). Only claims the touch via `onMoveShouldSetPanResponder` once movement is clearly horizontal (`dx > 15 && dx > 2×|dy|`) starting within the leftmost 40px — a plain tap (near-zero movement) never triggers it. **Refined after independent review**, which correctly pushed back on the first pass's code comment claiming descendant `Pressable`/`TextInput`s always get "first refusal" on a touch — RN's actual responder-termination default (`Pressability.js`'s `onResponderTerminationRequest: () => cancelable ?? true`) means an ancestor `PanResponder` *can* steal an in-progress touch, it's not structurally impossible, just gated tightly by the movement threshold. Since the new "Add a goal" `TextInput` (previous round) sits at `px-4` — inside the 40px zone — a deliberate horizontal text-selection drag started there was a genuine, if narrow, on-device-only-verifiable risk (the same failure class as the `inlineRem` bug above: looks fine in review, only provably wrong on a real device). Rather than rely solely on the movement-threshold gate, `backSwipe.panHandlers` was moved from the whole screen's outer `SafeAreaView` down to just the `KeyboardAvoidingView` wrapping the `FlatList` — structurally below the header *and* the Add-goal bar, so touches on that `TextInput` are outside this responder's view hierarchy entirely, not just gated by x-position. The two other `SafeAreaView` branches in this component (loading state, "goal no longer exists" state) still don't have the swipe handler — an accepted gap, both are transient/error states with no other navigation affordance either. Calls `router.back()` (guarded by `router.canGoBack()`, confirmed real on `useRouter()`'s return type) on release past a 70px threshold with vertical drift under 100px. Also switched from `useRef(PanResponder.create(...))` (re-allocates the config/closures every render, only `.current` ever kept) to a lazy-init ref, per review nit.

## 4. Operational gotcha: Expo SDK is pinned to 54 — don't casually bump it

This one cost real back-and-forth, so it's worth its own section. Expo Go builds are **SDK-locked**: a given Expo Go binary supports exactly the SDK it shipped with, not "that version or older." The project started on SDK 57 (npm's `latest` tag at the time), which produced "This project requires a newer version of Expo Go" — the intuitive read is "downgrade," so it went to SDK 56, which produced the *same error*. Root cause: the tester's actual installed Expo Go (checked via the app's own Profile screen, which reports its supported SDK number directly) was SDK 54. Matching the project to that number — not to whatever's newest upstream — fixed it.

**If Expo Go compatibility errors come up again:** check the installed Expo Go's own reported SDK version first, don't guess from `npm view expo dist-tags`. To actually change the SDK: `npx expo install expo@<version>` then `npx expo install --fix`, and by hand afterward — `--fix` doesn't catch these — (1) `@react-native/jest-preset` only exists as a separate package from RN 0.85 onward, remove it entirely on older SDKs and let `jest-expo` use RN's bundled preset instead; (2) `app.json`'s `plugins` array can end up referencing a package that doesn't export a config plugin at the older SDK's version. Full detail in [`TECH-STACK.md`](./TECH-STACK.md) §1's `expo` row.

## 5. What's genuinely not done

1. **Full on-device manual regression.** The app has now been run for real via Expo Go on the user's phone (see §1) — real progress over prior sessions — but that was ad-hoc use during this session's feature work, not the systematic checklist in [`TESTING.md`](./TESTING.md) §2, and specifically not yet against a standalone compiled `.apk` (Expo Go and a real binary can differ — config plugins, e.g. `expo-sqlite`'s, only actually run during a native build; see §3 above and the swipe-gesture entry above it for two examples of things that only surfaced under real on-device testing this session).
2. **An actual EAS build.** `eas.json` exists with Android-`.apk` profiles (`development`/`preview`/`production`), but running it needs an Expo account login (`eas login`, `eas init`) and, for a local build, Java 17 + the Android SDK on whatever machine runs it — see [`ENVIRONMENT-SETUP.md`](./ENVIRONMENT-SETUP.md) and [`BUILD-AND-EXPORT.md`](./BUILD-AND-EXPORT.md). Neither is set up in this sandbox as of this session.
3. **Export/import (JSON backup).** Listed in brief §10 as a stretch feature but flagged there as worth prioritizing given there's no cloud copy of data. Not built.

**Real app icon/splash artwork — now done**, moved out of this list. `assets/icon.png`, `android-icon-{foreground,background,monochrome}.png`, and `splash-icon.png` were replaced (same filenames/dimensions as the Expo template originals, so `app.json` needed no structural changes beyond updating `adaptiveIcon.backgroundColor` from the placeholder `#E6F4FE` to the new mark's actual brand blue `#2563eb`). The mark: a minimal root-and-two-branches node glyph — chosen because "Klados" is Greek for *branch* (κλάδος), and the glyph is literally the app's own goal-tree structure (a root branching into children) reduced to its simplest form, not an abstract/unrelated mark. Built as hand-written SVG rendered via `cairosvg` (installed into a throwaway venv, not a project dependency — ImageMagick's built-in SVG coder was tried first and silently dropped path elements; its `rsvg-convert` delegate wasn't installed and `apt`/global npm both lacked permissions in this sandbox, so a local Python venv was the path of least resistance). The foreground/monochrome adaptive-icon layers were deliberately sized and centered within Android's ~66%-of-canvas safe zone and verified against both a circle mask and a squircle mask before installing — nothing clips under either.

## 6. Process notes for continuing this project

- The four-stage workflow in [`.claude/CLAUDE.md`](../.claude/CLAUDE.md) was actually used throughout, not just written and ignored: `planning-analyst` at the start of new work, `solution-architect`-style reasoning before non-trivial decisions (done inline rather than always spawning the subagent, given the pace of this session), `independent-reviewer` after every real chunk of work (caught genuine bugs every single round — worth keeping this habit), `qa-tester` before declaring the whole thing "done." - Verification loop that held up well: `npx tsc --noEmit` → `npx jest` → `npx expo export -p android` (then delete the generated `dist/`) before calling anything checkpointed.
